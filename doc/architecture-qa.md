# Agent Runtime 架构问答


## 模块一：Context / Performance


### 1.2 session 聊了 200 轮 context 快爆，怎么做压缩？如何保证压缩后仍流畅？

可以在未压缩历史累积达到负荷阈值时启动压缩机制：在划定边界时通过智能回退确保工具调用与其返回结果成对完整而不被割裂，同时保留最近的对话轮次以保障即时上下文与细节追问，将更早的历史及既有摘要合并提炼为结构化增量摘要，并将生成的摘要打上独立系统标识注入上下文以构建长短期分层记忆、防止模型将历史要求当成新指令重复执行
同时还可以把原始的信息给存储起来，并在system prompt中增加引用，以确保模型可以追查到原始的压缩文本，减少信息的丢失。

## 模块二：Memory

### 2.1 熟悉半个月后，用户问了以前问过的问题，memory 召回如何做更合理？

可以在架构上由初期的全量轻量索引演进为基于语义与关键词的动态混合检索机制，按需从海量记忆向量库中召回高相关条目，同时为每条记忆注入写入时间戳与时效衰减权重以确保用户近期的最新习惯与偏好优先于陈旧习惯，在后台借助闲置周期的记忆整理机制对碎片化记录执行去重、冲突消解与失效标记以保证mem一致性，并在最终注入上下文时显式附带独立的来源与时间元数据标识
这一点可以参考 memos 的做法，如果meme冲突，也可以将他们放在一起用数据结构连接起来，召回的时候一并召回

## 模块三：Task

### 3.1 长程任务执行中忘掉目标：解决方案与优缺

可以采用重申目标、外置任务清单、摘要接力及多智能体分治等策略，因为单纯在提示词中复读目标治标不治本，外置清单高度依赖模型调用纪律，多智能体分工则面临系统复杂度与隐式上下文损耗，因此最稳健的工程做法是采取组合策略：在外层将大任务切分为拥有独立干净上下文的子任务，在执行中利用外置任务清单显式更新完成状态以推进任务流转，在压缩层借助结构化摘要将原始目标、当前进度与下一步行动如接力棒般持续传递，并在底层运行环境中设立最大执行轮数作为防死循环的安全兜底，从而在控制上下文膨胀的同时确保长链路任务始终锚定最终目标。
其实笔者写代码的工作流也是借鉴了这种思路，main agent 只负责记录 log，以及派发主要任务，所有的写代码 + 审核的工作都是sub agent完成的

## 模块四：Tool / Session Runtime

### 4.1 Agent 工具有同步和异步两类。异步工具不能让用户一直等，但结果依然重要。你会如何设计异步工具执行和完成通知？

可以先执行一会儿，超出的时间限制之后再将耗时工具放入后台并发执行并即时返回任务编号以避免当前对话卡死，把任务状态落盘持久化防止丢失，待任务完成后通过下次交互顺带带出、系统主动唤醒推送或由模型按需查询将结果交付用户

## 模块五：Agent Runtime 架构对比

### 5.1 Claude Code 的工具输出方式 vs OpenAI-compatible function calling

Claude 路线将工具输出直接作为原生文本流喂给模型，省去了文本转义与死板配对的束缚，但缺乏强校验且生态相对封闭；
而通用接口路线则将工具作为标准 JSON 接口调用，具备严格的参数校验与全行业通用性，但遇到大段日志时转义开销大，且要求调用与返回必须严格成对，稍有裁剪不当极易报错。
